# Умный кредитный кабинет предпринимателя — фронтенд

Прототип цифрового кредитного конвейера для малого и микробизнеса (кейс
Альфа-Банка). В одном продукте собраны клиентский путь — от потребности в
финансировании до выдачи денег — и рабочее место кредитного специалиста банка.

Сборщиков нет: React, Babel, Tailwind и Lucide подключаются через CDN, JSX
компилируется в браузере.

## Структура

```
index.html            точка входа: CDN, шрифт, ранняя установка темы, подключение файлов
styles.css            дизайн-система: токены светлой и тёмной темы, компоненты, адаптив
api.js                слой интеграции: мок-функции с контрактами эндпоинтов FastAPI
app.js                React-компоненты и состояние приложения (JSX)
assets/               иконки, иллюстрации, логотип, декор
Dockerfile            образ со статикой на nginx
docker-compose.yml    запуск одной командой
THIRD_PARTY_NOTICES.md сторонние компоненты и перечень смоделированных интеграций
```

## Запуск

**Локально в VS Code:** запустите бэкенд из папки `backend` в первом терминале:

```powershell
python -m uvicorn main:app --reload --port 8000
```

Во втором терминале из корня проекта запустите фронтенд:

```powershell
python -m http.server 5500
```

Откройте `http://localhost:5500`. Документация API доступна на `http://127.0.0.1:8000/docs`.

**Через Docker:** единый `docker-compose.yml` поднимает фронтенд, бэкенд и Ollama:

```bash
docker compose up --build
```

Фронтенд будет доступен на `http://localhost:8080`, документация API — на `http://localhost:8000/docs`.

Требования к окружению: любой современный браузер и доступ в интернет для CDN.
Серверная часть фронтенду не нужна — данные живут в памяти вкладки.

## Сквозной сценарий проверки (3 минуты)

1. **Вход** — поля заполнены тестовыми данными действующего клиента, нажать
   «Зарегистрироваться». Регистрация нового юрлица в сценарий не входит.
2. **Обзор** — карточка компании из ЕГРЮЛ, обороты, витрина продуктов.
   Нажать «Подобрать кредит».
3. **ИИ-ассистент** — выбрать подсказку «Нужен кредит 2 млн на закупку товара»,
   на вопрос о сроке ответить `12`. Ассистент подбирает продукт и считает платёж.
4. **Заявка** — параметры перенесены из диалога, калькулятор пересчитывает платёж
   на лету. Нажать «Отправить заявку».
5. **Статус** — этапы конвейера, балл скоринга с факторами, история заявки.
6. **Банк** — переключатель ролей в шапке. В очереди видна заявка клиента:
   «Одобрить», «Иные условия» или «Отклонить».
7. **Клиент → Статус заявки** — решение и комментарий банка видны сразу.
   Нажать «Принять предложение».
8. **Подписание** — отметить ознакомление с договором и ввести код подтверждения.
   Код показан под формой: внешних каналов в прототипе нет. Неверный код
   отклоняется.
9. **Выдача** — статус «Кредит выдан», сумма зачисления, счёт и дата первого
   платежа. Вся история этапов — в карточке справа.

Дополнительно: переключатель светлой и тёмной темы в шапке (выбор запоминается),
адаптив до ширины телефона — на узких экранах таблицы заявок превращаются в
карточки.

## Модель данных (фронтенд)

```
Company      name, inn, okved, age, revenue, employees, accountTurnover,
             preApprovedLimit, account
User         name, phone, role: client | bank
Product      id, name, rate, minAmount, maxAmount, minTerm, maxTerm, pledge,
             features[], purpose, defaultPurpose
Application  id, companyName, inn, productId, productName, rate, amount, term,
             purpose, documents[], payment, status, score, factors[],
             decisionComment, counterOffer?, signCode, account, createdAt,
             signedAt?, issuedAt?, firstPaymentDate?, history[]
HistoryEvent at, title, text
```

### Состояния заявки

```
draft → scoring → approved → signing → signed → issued
                ↘ counter  ↗
                ↘ rejected (финальное)
```

- `counter` — «одобрено на иных условиях»: банк предлагает меньшую сумму и
  больший срок, клиент принимает их на экране статуса.
- `signing` → `signed` → `issued` — принятие предложения, подписание кодом,
  перечисление денег.
- Скоринг отделён от решения: новая заявка всегда создаётся в статусе `scoring`.
  Результат модели хранится как предварительная рекомендация и не одобряет заявку.
  Финальное решение `approved`, `counter` или `rejected` может выставить только
  отдельный endpoint банковского решения; повторное решение и неправильные переходы
  статусов блокируются сервером.

## Контракт с бэкендом

Все обращения к серверу собраны в `api.js`. Перед каждой функцией оставлен
комментарий `// TODO: ИНТЕГРАЦИЯ ...` с целевым эндпоинтом — тело функции
меняется на `fetch`, остальной код не трогается. Базовый адрес — `API_BASE_URL`.

| Функция | Метод и путь | Назначение |
|---|---|---|
| `apiLogin(phone, name, company)` | `POST /api/auth/login` | Вход, профиль компании из ЕГРЮЛ/ЕГРИП |
| `apiSendChatMessage(text, history)` | `POST /api/chat` | Ответ ассистента и рекомендация продукта |
| `apiCreateApplication(data)` | `POST /api/applications` | Создание заявки, запуск скоринга |
| `apiGetApplications()` | `GET /api/applications` | Список заявок для кабинета и CRM |
| `apiBankDecision(id, status, comment)` | `PATCH /api/applications/{id}/decision` | Решение банка по заявке |
| `apiAcceptOffer(id)` | `POST /api/applications/{id}/offer/accept` | Клиент принимает предложение, формируются документы |
| `apiSignDocuments(id, code)` | `POST /api/applications/{id}/sign` | Подписание кодом подтверждения |
| `apiDisburse(id)` | `POST /api/applications/{id}/disburse` | Перечисление средств на счёт |

Сейчас данные живут в объекте `STORE` внутри `api.js` и сбрасываются при
перезагрузке страницы. Сетевая задержка имитируется через `setTimeout`.

ИИ-ассистент вызывается только через собственный бэкенд: фронтенд знает адрес
своего API и не обращается к провайдеру модели напрямую. На сервере
предполагается модель с открытыми весами и OpenAI-совместимый интерфейс, поэтому
провайдер меняется переменными окружения (`LLM_BASE_URL`, `LLM_MODEL`).

## Дизайн-система и темы

Токены заданы в `:root` файла `styles.css`, тёмная тема переопределяет те же
переменные в `:root[data-theme="dark"]` — разметка и компоненты общие.

Светлая тема: `#EF3123` (основной), `#C8241A` (нажатие), `#FFE9E7` (подложка),
`#F5F5F7` (фон), `#1F1F1F` (текст), `#6B6B6B` (второстепенный).
Тёмная тема: `#FF4F3F` (основной), `#0E0F12` (фон), `#17181D` (поверхности),
`#ECEDF1` (текст). Шрифт Inter, скругления 16 px для карточек и 12 px для кнопок
и полей.

Выбор темы хранится в `localStorage` (`akk-theme`), при первом открытии
используется системная настройка `prefers-color-scheme`. Тема применяется в
`index.html` до отрисовки, поэтому вспышки светлого фона нет. Переход между
темами анимирован и отключается при `prefers-reduced-motion`.

Tailwind подключён и сконфигурирован теми же цветами (`primary`, `primary-dark`,
`primary-light`, `bg`, `ink`, `muted`) — можно пользоваться утилитами при
доработке. Preflight отключён, чтобы не конфликтовать с `styles.css`.

## Адаптив

| Ширина | Поведение |
|---|---|
| > 1100 px | Сайдбар, двухколоночные экраны заявки и чата |
| ≤ 1100 px | Экран заявки и чат — в одну колонку |
| ≤ 980 px | Сайдбар переезжает в верхнюю панель, трекер этапов становится вертикальным, продукты в две колонки |
| ≤ 860 px | Таблицы заявок превращаются в карточки с подписями полей — без горизонтального скролла |
| ≤ 560 px | Уплотнённые отступы и шрифты, кнопки на всю ширину, в переключателе темы остаётся иконка |

## Допущения и ограничения

- Данные синтетические, реальные операции и платежи не выполняются.
- Клиенты — действующие ИП и юридические лица; регистрация нового бизнеса в
  сценарий не входит.
- Авторизация демонстрационная: пароля, сессии и проверки телефона нет.
- Весь путь проходит внутри продукта: SMS, почта, мессенджеры и звонки не
  используются, код подтверждения показывается на экране.
- Загруженные в заявку файлы на сервер не передаются — показывается только их
  список.
- Внешние проверки (ЕГРЮЛ/ЕГРИП, бюро кредитных историй) смоделированы;
  перечень моков — в `THIRD_PARTY_NOTICES.md`.
- Babel компилирует JSX в браузере. Для продакшена код нужно собирать заранее.
